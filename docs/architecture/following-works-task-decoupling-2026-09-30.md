# 关注刷新与作者作品同步任务解耦

> 2026-09-30 纠正。此前“已经完全解耦”的表述不准确：当时正式 `TaskRunner.onEnvelope` 在关注结果入库后仍自动创建作品任务，单作品隔离 run 也预建了一个未执行的关注任务。当前改动移除了这两处依赖。

## 两个动作的边界

| 用户动作 | 唯一允许排入的采集任务 | 输入与结果 | 不应发生的副作用 |
|---|---|---|---|
| 刷新账号关注目录 | `collection.following` | 当前账号、确认的作者上限；只更新关注作者与刷新检查点 | 不打开作者作品页，不创建 `collection.creator_works`、评论、媒体或云任务 |
| 同步一位已保存作者的作品 | `collection.creator_works` | 当前 owner 的已验证 `uid`、独立 `sec_uid`、主页和作品上限；只写作品与作品检查点 | 不重新读取本人关注列表，不创建 `collection.following` 或评论任务 |
| 按需补充某作品评论 | `collection.work_comments` | 已入库作品的原生 ID 和评论上限 | 不刷新关注，不重新抓作者作品 |

`TaskRunner.startFollowingRefresh` 只排关注任务。收到关注 envelope 后，主进程只持久化关注结果并完成该任务；不会顺带创建作品任务。`TaskRunner.startCreatorWorksSync` 是独立入口，必须从 schema v6 中读取当前 owner 的已验证作者双 ID；关注刷新任务即使处于失败状态，也不阻止已保存作者的作品任务创建。桌面端相应提供独立的“刷新关注目录”和“同步此作者作品”控件；生产能力门仍关闭。

每类任务的 payload 与去重指纹只保留自己的范围：关注任务仅有作者上限，作品任务仅有作品上限，评论任务仅有评论上限；其它两项在内部指纹合同中为 `NULL`。旧的三项合并 `SampleSyncOptions`、`startSampleSync` 和 `sync:start` 入口已删除。能力门关闭时，队列调度器也不会执行已有的结构化采集任务。

隔离单作品试跑只创建作品任务。它读取此前验证的目录，但不会创建或执行关注刷新任务。历史 2026-09-30 run `r8-homepage-client-20260930065027-7ce58f08` 在本次纠正前生成，数据库中确实有一个 `paused` 关注任务；原始证据保持原样，不回写或改造。新版离线与打包检查要求新 run 中关注任务数为零。

## 验证与剩余门槛

- 离线测试要证明：关注成功后只有关注任务和作者记录；即使再次调度也没有作品命令。另一个测试把关注任务置为阻断，仍能从已验证 v6 作者目录显式排作品任务。隔离试跑测试只允许一个作品任务。
- 正式 schema 仍为 v5，正式生产能力门仍为 `false`。生产连接器的作品证明目前仍混用 `uid/sec_uid`，低请求量路径尚未作为正式作品连接器接线；关注多页协议也未独立验收。因此这次改变是**任务行为和客户端操作边界的修正**，不代表两种真实生产同步已经开放。
