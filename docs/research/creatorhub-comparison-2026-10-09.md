# CreatorHub 与 Signal Desk 已实现能力对比

分析日期：2026-10-09。

用户补充后的解释与规划以[浏览器、接口与风险复核](creatorhub-browser-risk-followup-2026-10-09.md)和[关注关系及取关分区方案](../architecture/following-relationship-reconciliation-plan-2026-10-09.md)为准。作品详情、评论、通知、后台运行和安装升级原本已在产品设想中；“未实现”不代表“此前没有规划”。后台采集须等作品/评论链路稳定后再加入，发布暂不纳入范围。本轮只分析和确定方案，不修改产品代码。

结论：CreatorHub 在多平台运营功能、作品与评论监控、下载发布和持续调度方面覆盖更广；Signal Desk 在已实现的抖音博主长期资料管理、身份与字段核验、发布频率判断、异常隔离和飞书同步方面更贴近本项目目标。建议保留现有数据与核验核心，借鉴 CreatorHub 的任务产品化设计，并将其采集实现作为待验证的参考。

本报告检查了双方源码、测试代码与维护文档，没有运行 CreatorHub、登录平台或执行真实采集，也没有重新运行双方测试。对 CreatorHub 的“已实现”判断表示主分支中有相应实现，不等于本机真实验收通过。对 Signal Desk 的真实验证结果引用现有验收记录，未当作本轮新测结果。

**功能范围对比**

| 维度 | CreatorHub 主分支 | 本项目已实现部分 | 对本项目的意义 |
|---|---|---|---|
| 产品中心 | 多平台账号、采集任务、作品、评论、下载、发布与互动 | 抖音关注博主的长期资料、发布状态与检查优先级 | 两者主要管理对象不同 |
| 平台 | 抖音、小红书、快手、视频号；能力按平台不同 | 日常可用链路集中在抖音；通用适配器代码不计为其他平台已落地 | 多平台覆盖是明确差距 |
| 桌面与服务 | Python/FastAPI、SQLModel/SQLite；React 工作台；Windows 启动中心使用 pywebview/WebView2 | Electron、React、TypeScript、SQLite；Chrome 扩展、Native Messaging；另有 Python 媒体工作器 | 不能直接合并运行架构 |
| 浏览器与账号 | 每账号独立 Profile；CDP/Patchright；代理、浏览器后端及账号环境管理 | 选择 Chrome 配置，通过扩展连接并核验实际登录账号，按账号隔离资料 | 前者账号环境管理更广；后者已有业务归属约束 |
| 关注列表 | 抖音 API/browser/hybrid，完整分页、后台进度、取消、服务端分页显示；成功后替换当前关系快照 | 完整分页、逐页保存、主页身份去重、累计展示、缺失基础资料单独补全 | 读取手段可研究，存储语义不可照搬 |
| 博主资料保留 | FollowEdge 是当前关注/粉丝关系；MonitorTarget 有别名、分组、标签 | 原记录身份、星标、批注、历史快照持续保留；部分、空结果不删除历史博主 | 本项目长期资料库能力应保留 |
| 主页状态与频率 | 可配置监控轮询间隔，保存扫描时间和新作品；未发现与本项目等价的博主发布间隔分级 | 主页作品数、最近发布时间、平均发布间隔、四档频率、30 天无更新规则、手动加降权 | “多久检查”不等于“博主多久发布” |
| 身份与来源 | 账号/任务关联、来源任务、抓取时间、任务 ID 不复用；有部分身份校验 | 当前登录账号、目标作者 UID/secUid、请求来源、作品可见性、游标和时间范围共同复核 | 来源任务可追踪与作品确属该作者是不同层次 |
| 数据异常 | 风控、登录失效、网络错误、任务阻塞等集中管理 | 作品净增≥10、增量解释不足、未衔接旧作品等进入异常组；隔离旧有效基线，显式单作者补齐 | 两种“异常”应分别建模 |
| 作品详情与评论 | 有作品、评论、弹幕监控和持久化代码；评论任务独立 | 主页状态使用必要作品列表，但正式作品详情/评论采集能力门仍关闭 | 这是内容采集闭环上的主要差距 |
| 关键词发现 | 抖音、小红书批量关键词采集、筛选、续跑、导出；小红书部分功能列为未发布 | 未形成已验收日常功能 | 适合后续拓展新博主、新内容来源 |
| 持续运行 | 服务运行时循环扫描；任务间隔、错峰、风险延后、恢复；发布等任务持久化 | 点击启动后程序连续执行，支持取消与继续原剩余名单；尚无后台定时采集 | 本项目已有流程自动化，缺的是定时触发和统一运行管理 |

| 下载与发布 | 媒体下载、断点续传、共享路径锁、发布、跨平台转发、评论/私信互动 | 有媒体处理、分析和导出代码，但正式采集未验收；没有完整的运营发布闭环 | 不应将本地原型计为成熟功能，也不必把全部运营功能纳入当前目标 |
| 博主表格与飞书 | 任务/内容表格、筛选、Excel 报告；未发现等价的博主自定义表格及飞书同步实现 | 自动五列、自定义文本/整数/日期、排序筛选、发布间隔图表、虚拟列表；飞书单条/全库/自动同步 | 本项目已有可持续使用的资料管理闭环 |
| 安装与升级 | Windows 安装器、更新检查、增量优先、断点续传、备份与回滚设计 | Windows 打包与日常部署、打包冒烟；未发现等价的应用内增量更新系统 | 用户分发扩大时值得借鉴 |

平台能力需要逐项看源码。CreatorHub README 的本账号管理表包含小红书关注/粉丝，但其 [transport_matrix.py](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/transport_matrix.py#L59) 将该项标为 `unavailable`，说明网页端未提供该列表；仓库同时保留浏览器探索代码。应将这项视为声明与能力矩阵存在差异，不能按表格直接认定可用。视频号也明确限定为本账号创作者助手数据。

**最影响复用判断的四个差异**

1. 关注关系快照与长期博主资料库需要分开。

   CreatorHub 的 `_replace_follow_snapshot()` 按 `account_id + direction` 在一个事务中删除旧 FollowEdge，再插入本轮结果。异常响应会保留旧快照，明确有效的空列表则允许清空。这适合表达“目前关注谁”，并非随意删除；但与本项目“曾收录的博主持续保留”要求不同。

   本项目 `savePlanRows()` 追加观察、核对 UID 与主页身份；展示时按账号和 secUid 取最新资料，并保留原始记录 ID 与批注。若未来引入 CreatorHub 的读取器，结果必须经过本项目现有归属验收与累计保存层，不能直接导入其关系表替换策略。

   证据：[CreatorHub 快照替换](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/main.py#L3526)、[空结果判定](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/main.py#L3660)、[本项目目录保存与展示](../../src/main/followingDirectoryStore.ts)、[累计保留测试](../../src/main/followingDirectoryStore.test.ts)。

2. CreatorHub 的监控周期与本项目的发布频率不能相互替代。

   CreatorHub 的 `interval_seconds` 表示任务多久再执行一次；默认首次只采集订阅后的内容，可显式设置历史回填。Signal Desk 的平均间隔来自身份、公开状态、日期都有效的作品，计算 n 条作品的 n−1 个间隔，再结合最近成功核验时的发布状态分档。

   本项目还明确区分主页总数与已保存作品数、发布时间与检查时间、个人平均与账号层面的等权平均。CreatorHub 的新作品列表可以成为后续候选数据来源，但不能跳过完整性判断直接替换这些统计口径。

   证据：[CreatorHub 监控模型](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/models.py#L109)、[首轮回填测试](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/tests/test_douyin_monitor.py)、[本项目平均间隔](../../src/shared/creatorPublicationInterval.ts)、[频率和近期状态规则](../../src/shared/creatorRefreshPolicy.ts)。

3. API 能力标签不能证明主页采集已不依赖浏览器，也不能证明更快。

   CreatorHub 的抖音关注读取确实有带分页状态的直连实现；但查阅的抖音主页作品监控路径 `_scan_target_locked()` 调用 `fetch_videos()`，后者新建页面、导航目标主页、等待、滚动并监听作品响应。这条具体路径仍使用浏览器，尽管能力矩阵将公开监控归入 API/browser 可配置能力。

   该读取函数按作品接口 URL 收集列表，主要按作品 ID 去重；在这条具体函数及其直接入库路径中，未看到与本项目等价的逐作品 UID/secUid 双重归属和公开状态验收。该结论只针对所查路径，不代表 CreatorHub 全项目没有身份校验，也不代表已复现错归属。

   因此它提供采集实现参考，不能作为本项目正式作品/评论 R8 功能门可以打开的依据。若考虑接入，应先用少量同一作者样本核对身份、列表边界、置顶影响、发布时间和失败行为。

   证据：[直连关注分页](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/platforms/douyin/client.py#L954)、[抖音监控调用与保存](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/engine/monitor.py#L1491)、[主页读取](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/browser/fetcher.py#L219)、[本项目活动验收](../../src/shared/creatorActivity.ts)。

4. 自动运行与有效数据基线应继续解耦。

   CreatorHub 有服务循环、调度时间计算、任务阻塞原因、账号风险状态、持久化写任务，以及中断写入标为 uncertain 而不自动重发的设计。尤其 `cadence.py` 让调度器和界面共用下次执行时间，并用稳定的正向抖动避免轮询或重启反复改变计划。

   Signal Desk 已经由程序连续完成浏览器读取、去重、校验、入库和界面更新，不需要代理逐作者驱动。下一层可借鉴的是“何时自动触发、为何等待、如何恢复”的产品能力，而不是重写已有采集流程。账号级风控等待也不能替代本项目的作品缺口异常隔离。

   证据：[CreatorHub 运行循环](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/engine/monitor.py#L721)、[调度时间计算](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/engine/cadence.py)、[中断任务恢复](https://github.com/3441293738/creatorhub/blob/037f8b39387a715ef7ef7a28a22a66770e22fd67/app/engine/monitor.py#L309)、[本项目状态服务](../../src/main/creatorActivityService.ts)。

**本项目当前应保留的能力与仍存在的缺口**

累计目录、星标批注保留、账号隔离与作品字段归属不是展示层的小差别，而是当前数据可靠性的基础。异常结果引用不可变原始快照，未补齐前不覆盖有效基线；这是与频率判断、自定义资料和飞书同步相互依赖的一组能力，迁移采集器时应整体保留。

飞书已不是规划功能。2026-10-08 验收文档记录了 295 位博主的首次全库/自动同步、随后无重复复核，以及原有非 APP 记录保留；这仅说明该次账号与租户的验证范围，不代表所有账号或长期断网场景都已验证。[飞书接入与验收范围](../architecture/feishu-creator-database.md)

同时，本项目当前有三个不能回避的边界：

- `STRUCTURED_SYNC_AVAILABLE = false`；作品详情和评论有源码及测试，尚不能作为已开放产品能力。[功能门](../../src/shared/featureFlags.ts)
- 常规刷新在主页总数相同且没有可用原生列表时，仍允许仅计数跳过；它不能证明新增和删除没有相互抵消。[当前交接](../handoff/README.md)
- 尚未提供后台定时采集；建议检查周期 1/7/14/30 天与用户手动启动后的连续执行是现有能力，自动按时启动仍待实现。

2026-10-09 保存的验证记录为：46 组应用测试 437 项通过、浏览器关注/状态等测试 109 项通过，另有构建与打包验证。正式 R8 前置门禁仍退出 1，原因包括生产作品证明 UID/secUid 未独立绑定、逐候选导航、未接入有界主页采集器、生产命令缺独立作者 secUid。这些是历史记录引用，本轮没有重新执行。[验证原始摘要](../evidence/workspace-cleanup-20261009/validation.json)

**建议实施顺序**

| 优先级 | 建议 | 可借鉴内容 | 进入下一步前的可审阅结果 |
|---|---|---|---|
| P0 | 完成一个作者的正式作品采集闭环，再扩展单作品评论 | CreatorHub 的列表/详情/评论读取、置顶边界、首次回填逻辑 | 少量真实样本逐字段和归属核对通过；既有博主与批注不变；生产链路接通且相应门禁满足 |
| 链路稳定后 | 按原有规划，基于现有四档建立可选自动检查与通知 | `cadence.py`、监控循环、任务延后状态、通知模块 | 作品详情和评论采集先稳定；再验证一组低量任务，可暂停，重启不重复，断线停止，异常作者不混入普通批次 |
| P1 | 增加统一任务视图与来源追溯 | 任务队列、来源任务、抓取时间与发布时间分别筛选 | 用户能看到待处理/运行/等待/失败原因，跳转原博主或作品；旧批次证据保留 |
| P2 | 逐个平台增加读取适配器 | 平台能力矩阵与登录态隔离设计 | 每个平台先验证一位真实作者、一个真实作品，不把声明表当验收 |
| 功能完善稳定后 | 按原有规划完善安装升级与备份恢复 | 桌面更新、断点续传、增量回退 | 独立测试资料下完成升级、失败恢复和数据保持验证 |
| 当前不纳入 | 自动发布、私信、关注和评论运营 | 仅在产品目标明确扩展时研究 | 当前重点是完整采集链路，发布暂不计划实现 |

比较采集性能时，应对同一登录账号、同一组作者和同等字段分别记录冷/热启动，主指标从用户点击开始到资料及头像实际可用，包含浏览器准备、读取、校验、保存、资源加载、界面更新和计划等待。页面读取耗时、数据库写入耗时以及飞书同步耗时另列；CreatorHub 的秒级间隔配置和大规模快照测试不能换算成端到端速度优势。本轮没有可比实测数据，因此不提供谁快多少的结论。

工程上更合适的接入边界是“读取适配器输出候选数据 → 本项目归属/完整性验收 → 累计保存及异常基线 → 资料库与飞书投影”。Python 与 TypeScript 栈的差异只是实现成本，真正需要守住的是数据语义与验收边界。

若后续决定直接引入代码，还需先核对授权：本次检出的仓库未见覆盖整个项目的顶层 LICENSE，检出的许可文件主要属于第三方依赖；公开可读不能直接当作已获明确再分发许可。本次仅做实现分析，没有移植代码。
