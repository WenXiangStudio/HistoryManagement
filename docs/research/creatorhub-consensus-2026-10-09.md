# CreatorHub 对比讨论：已确认共识与后续参考

确认日期：2026-10-09。用户确认保存本轮讨论，用于后续借鉴参考。本文件记录产品方向与选型共识，不表示相关待办已经实现，也不启动功能开发、平台采集或架构迁移。

## 已确认的总体判断

**本项目的优势是轻量、架构简单、维护成本低、路线更自然简单，更符合个人初期使用。CreatorHub 的优势是工程化程度高，面向多平台、多账号和多类任务的架构路线更成熟。**

当前继续沿用本项目已经验证的浏览器读取与资料管理路线，保留累计博主档案、身份与字段校验、发布频率分组、异常基线隔离和飞书同步。后续按实际需求参考 CreatorHub 的工程实现，不将它的全部功能和架构作为必须追齐的目标。

这里的“成熟”主要指账号环境管理、任务调度、运行状态、失败处理与分发升级的工程覆盖；现有公开证据不足以比较双方封控率，也不足以认定 CreatorHub 在数百目标长期高频运行时有经过验证的安全边界。

## 需要长期保留的技术认识

- 本项目也使用抖音网页接口：优先复用真实 Chrome 页面已有响应，必要时在页面内主动 GET，沿用当前浏览器登录态。CreatorHub 部分 API 通道由 Python 在浏览器外维护 Cookie、参数与签名；另有浏览器读取路线，不能把整套系统概括为单一 API 模式。
- 浏览器进程与连接的稳定、数据字段与归属的可靠、平台账号的风控风险，需要分别判断。代码工程化程度高不能直接换算成账号封控概率低。
- CreatorHub 有限流、休息、额度、冷却与恢复控制，但部分限制作用于逻辑操作；一次操作可包含多次请求。程序配置不是平台认可的安全阈值，列表容量测试也不是高频真实采集的风险测试。
- GET/POST 不能单独代表风险等级。比较时应看业务动作、频率、累计量、分页深度以及失败后的处理；本机 APP 上报与平台业务写入分开统计。
- 295 位被观察博主与 295 个登录执行账号是不同规模。未来测试记录应同时说明执行账号数、目标数、运行时长和请求范围，并区分验证码、限流、登录失效、浏览器故障和封禁。
- 继续按现有原则控制范围：少量真实验证先行，减少重复请求，有界读取，明确拒绝或异常时停止；全程耗时从点击开始到资料与头像实际可用，阶段耗时单列。

## 关注关系与长期档案的共识

累计资料库保留历史博主，同时同步最新关注关系。可靠完整同步确认 295 位变为 293 位时，原 2 位进入“取关”分区，累计收录仍为 295 位；原记录身份、星标、批注、自定义资料和历史证据保持不变。

按账号和主页身份比较清单，不能只比较总数或昵称；部分采集、失败和不确定空结果不能将缺失者判为取关。重新关注时复用原档案。取关作者默认退出常规批量刷新和未来自动监控，保留历史查看；飞书不因取关删除记录。具体接入、完整性依据和验收场景见下列方案。
