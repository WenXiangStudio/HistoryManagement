# 加／降权误拦截与内容任务结束通知修复：APP 0.1.41

用户反馈：点击博主卡片加／降权，报 `creators:priority-update` 的“请等待本轮同步或资料刷新完成，或取消后再切换账号”；任务中心截图显示活跃度基线169/169已完成，用户要求修复任务完成后的退出机制。

正式现场只读核对：关注同步idle、基础资料idle、活跃度completed、视频采集completed、连接online/ready，数据库没有running/queued的内容批次或分析批次。进一步检查当前主进程内存，videoContent、doubaoSpeech、videoWorkflow均running=false，所有abort引用为空，workflow队列长度0；没有发现169/169基线任务持续持有运行锁。两条研究报告已由用户重试完成，分别为北京时间18:47:57及18:51:07。现场无法回溯确认报错瞬间具体哪一个内容任务正在运行，不能把历史基线认定为仍运行。

确认并复现两处代码问题：

1. `updateCreatorPriority`复用了切换账号的`requireAccountIdle`。该保护同时检查视频采集、日期查找、语音与研究处理；前端权重按钮只按关注同步、基础资料补充、博主资料刷新禁用，因此独立内容处理期间按钮可点，后端却拒绝，并显示与当前操作不符的“切换账号”错误。
2. `VideoWorkflowService`在finally中先保存并通知完成结果，随后才释放abort／activeBatch。在成功、部分失败和取消三条路径，通知时仍可读到running=true。测试对这三条路径均在修复前复现失败；同一测试修复后通过。

权重修改现在由前后端共享`creatorPriorityBusyReason`：只在关注同步准备／进行中、基础资料补充、博主资料刷新实际进行中阻止修改，并显示具体任务名称；独立视频采集、转写、研究任务不阻止本机权重保存。账号切换仍沿用完整保护；博主归属、账号、异常基线、revision和手动等级算法保留。

内容任务先清除本轮abort／activeBatch并停止本轮工作器，再保存终态并通知界面。队列仍有待执行作品时running仍为true，避免完成一条被误当作全部空闲。报告额度128000、15分钟等待和已有正文／报告质量门保留。
