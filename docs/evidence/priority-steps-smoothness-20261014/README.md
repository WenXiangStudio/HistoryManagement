# 连续调档与资料库交互优化：APP 0.1.43

用户反馈两个问题：加权／降权最多一档，再点会关闭；点击后整个区域操作仍发卡。本次从0.1.42的实际实现与同一302位资料副本继续修复。

## 操作规则

- 加权／降权改为从当前已保存的生效等级逐档升降：极低频 ⇄ 低频 ⇄ 中频 ⇄ 高频；相同方向可连续操作。
- 最高档禁用加权、最低档禁用降权。后端也钳制边界，越界请求不写入、不增加revision。
- 独立“恢复自动”按钮清除人工等级，按最新发布间隔与核验结果重新分类。再次点方向按钮不再关闭。
- 保留已有人工等级与revision，无数据迁移。mode记录最后一次调整方向；tier为持久化人工等级。未知等级沿用原有入口规则。
- 每次从数据库事务内读取的当前等级出发，校验revision，拒绝同一次请求的重复投递／过期版本。归属、账号与采集任务保护保留。

## 卡顿来源与修复

0.1.42虽然只给目标博主装饰结果，底层活动快照、旧基线与计数基线仍进行账号范围读取；状态查询还解析整批基线JSON以计算人数。前端保存中／提示／权重变化重新构造全部卡片，昵称Context更新传播到全部名字，五秒空闲刷新继续读取整库，人工昵称持续播放background-position渐变动画。

本次将主页筛选下推到资料目录、权重、活动快照／尝试、两类基线与冷态发布时间来源查询；完整账号缓存可复用，单主页冷态结果不污染完整缓存。状态人数直接COUNT DISTINCT，不解析所有基线。定时空闲刷新仅查仪表盘、队列与运行状态；资料变化事件、搜索与窗口focus读取完整资料，采集运行期间及完成后的首次轮询仍完整读取。

卡片拆为memo组件，事件处理器保持引用稳定，批注编辑在卡片内部；IPC完整读取复用内容相同的博主对象与数组，跨周显示投影按源对象／日期缓存。昵称采用按身份订阅，只更新外观改变的名字；保留紫色渐变和光晕，移除持续动画。成功前不预先移动分组，保存失败保留旧状态，只在当前卡片显示保存中。

## 实测

前后使用本次正式现场同一份302位真实资料副本，同一位自动高频博主，6次降一档／恢复自动操作。0.1.42恢复自动通过再次点降权；0.1.43使用独立恢复自动按钮。GPU正常开启，前台窗口；点击计时等待已保存分组变化与提示实际渲染。保存后继续观察约1.2秒，注入滚轮操作；另有5.5秒含状态轮询的静置和连续30次滚轮测试。

| 点击到已保存结果实际显示 | 0.1.42 | 0.1.43最终候选 |
| --- | ---: | ---: |
| 6次均值 | 96.5 ms | 34.5 ms |
| 范围 | 80.2～113.6 ms | 31.5～38.5 ms |

均值减少约64.3%。这是本机副本测量，不能当成所有设备的延迟保证。观察窗口内前后均无超过50ms的渲染JS longtask；最终版静置含轮询帧间隔最大16.8ms，连续滚动最大50ms；点击后的滚动样本仍记录一次66.6ms帧间隔，不能宣称所有操作绝对零掉帧。独立回归证明40卡片下改一张只渲染目标卡片、相同IPC数据与空闲轮询不重绘卡片，权重分组移出不重绘剩余39张；昵称仅通知改变的身份。

原始结果：`local-data/priority-steps-smoothness-20261014/before-smoothness.json`、`release-after-smoothness.json`。中间`after-smoothness.json`与打包冒烟窗口并行，候选被遮挡导致rAF暂停／15秒异常样本，静置帧数为0，保留记录但不用于对比；最终候选测量串行且显式bringToFront。另有两份中间有效候选记录保留，各自对应当时构建。
