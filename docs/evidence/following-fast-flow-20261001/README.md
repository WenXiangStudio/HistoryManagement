# 关注资料全程自动化与提速真实验证 · 2026-10-01

用户授权从整体流程优化速度，不局限于局部调整。原第三批由代理逐步骤发命令，页面采集虽然只用 5.4 秒，从首份测试文本到完成进度回复却经过 127.587 秒。本轮已将日常执行链改为 APP 和扩展一次连续完成。

## 最终实现

1. APP 选择新增 10 或 20 位，点击同步后生成本轮范围和已有作者身份名单。配置页连接已更新扩展后自动开始，不再等待用户第二次点击或代理发送下一条命令。
2. 浏览器优先复用已有本人主页标签；仅在页面不存在或内容脚本尚未就绪时创建/刷新。直接打开关注弹窗，按真实节点出现判断就绪。
3. 桌面诊断和扩展使用同一份 `following-batch.js`。昵称/简介保留图片形式 emoji，头像与同卡片唯一主页身份绑定；直播头像按同卡片核对，不打开作者主页。
4. 已加载图片立即核验；未加载图片按事件并发等待。取消每位固定 250 ms 的串行等待，不通过同时请求平台接口加速。
5. 浏览器将完整采集及绑定证据一次回传 APP。主进程校验账号显示名、范围、重复身份、字段/头像归属、原生身份缺失和来源边界，使用已有 SQLite store 事务保存并回读。
6. APP 通过数据更新事件刷新资料库，不等五秒定时刷新。界面确认累计资料和全部真实头像加载后回执；从点击开始到这一回执的时间是主要全程指标。
7. 资料报告、来源绑定、获取计时、保存计时、显示计时和失败信息自动存入 run 目录。日常路径不需要剪贴板 JSON、临时页面文本、人工命令回传或重复打包。

生产作品和评论能力门仍关闭。此次自动化入口只负责关注资料。

两个正常运行样本已证明 APP → Chrome 扩展 → 本人关注弹窗 → 自动回传 → SQLite → APP 全程可完成。它们不是冷启动、所有账号或完整 292 位关注分页的性能保证。首次扩展安装/更新、开发修复和本轮回归时间不在每次正常同步指标中；配置页等待首次连接仍会被 APP 起始时钟计入。

提取器另做过已加载页面只读核验：原第三批同二十位字段一致，页面提取 9.4 ms。这只是提取阶段诊断，不用它替代全程秒级指标。

## 数据与归属核验

- review APP 目录追加二十位，累计六十个不同 `sec_uid`；原四十位所有行、星标/批注和历史报告未改动。
- 新二十位与旧四十位重复 0；APP 六十张卡片、六十个实际加载头像和主页，新增字段逐条等于归属证据。
- 目录完整性 `ok`，外键违规 0；作品、评论、指标、任务和分析均为 0。
- 采集字段来源仍是当前登录账号公开可见页面。数值作者 `uid` 和原生 owner `sec_uid` 没有验证，继续 NULL；账号归属使用当前页面显示名称核对，不能称作原生 owner 隔离已验收。
- APP 目录是本轮唯一写入的产品库；原 `local-data/douyin-following.sqlite` 仍保存前三批四十位作为历史独立产物，没有复制出第二份日常业务库。后续排除名单以 APP 目录为准。

## 失败与修正

只读提取器调试曾遇到卡片未就绪和昵称头像尚未挂载，已增加 DOM 事件等待，错误头像匹配仍阻断。首次 APP 自动测试在约 1.176 秒因 owner 头像未完成挂载而阻断，未写数据；改为等真实 owner 头像出现后核对。原始阻断报告保留。

另一次基准工具误读取上一 run 的 blocked 状态，实际没有启动新 run，未计为采集结果；工具现等待新 run ID 才判断完成。正常链路没有自动修改代码或无限重试；遇到登录/安全验证/字段归属不一致仍停止。
