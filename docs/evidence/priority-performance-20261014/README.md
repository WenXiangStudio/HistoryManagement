# 加／降权响应速度优化：APP 0.1.42

用户反馈：加权、降权后接近1秒卡顿，要求提升流畅性。先在当前302位真实博主资料的隔离副本复现，再比较同一份资料、同一位博主、相同6次开启／关闭操作。

| 指标 | 0.1.41 | 0.1.42 |
| --- | ---: | ---: |
| 点击到已保存结果实际渲染，6次均值 | 873.8 ms | 93.3 ms |
| 点击到已保存结果实际渲染，范围 | 794.6～1165.9 ms | 82.0～100.3 ms |
| 独立IPC回执阶段，含读取当前账号配置 | 236.3 ms | 63.5 ms |

以上全程从按钮点击开始，等待已确认的权重／分组变化及成功提示出现，再经过requestAnimationFrame确认可展示；不是以某个保存阶段替代点击到界面可用的全程。均值缩短约89.3%。两版本测试窗口均记录渲染longtask，样本期间没有超过50ms的渲染长任务；主要延迟来自等待主进程读取与整页刷新。此为本机相同副本的6次验证，不外推所有设备与资料规模。

原因：后端为保存一位博主的权重，先装饰全库302位的活动与基线资料；保存时全局data:changed触发一次App全量refresh，操作回调又显式await refresh。每次refresh并行请求仪表盘、旧收件箱、全部博主、队列、设置、完整同步状态、配置和兴趣作品；保存期间global busy禁用其他卡片。读取与数据传输重复，用户等待约1秒才见到结果。

本次变更：

- 后端从当前账号目录按主页身份选出目标博主，只对该位计算活动资料并验证权重。仍检查账号、异常基线、revision和实际博主同步／刷新任务，不使用前端数据决定最终等级。
- 事务提交成功后发送带owner、secUid、priority、revision的creator-priority事件。App识别此事件后，直接更新匹配的已确认权重、分组计数、昵称颜色及刷新间隔，不因这次事件或成功回调读取整页资料。
- 操作返回前显示该位“保存中”，仅禁用该博主的权重按钮；其他博主可独立保存。成功前不预先修改权重或移动分组；失败保留原状态并读取当前资料核对。
- 事件和回执通过同一通道应用，按revision去重并忽略迟到结果；账号切换后不显示前账号成功提示。即使较旧的全量读取随后返回，也不会覆盖刚确认的新权重。原定时刷新和其他数据变更事件继续保留。

验证：76组630项应用测试、TypeScript、编译、Windows打包及packaged-renderer启动／IPC检查通过。新增5项回归覆盖仅装饰目标身份、保存无需全量读取、只禁用目标且可并行保存另一位、同名不同身份／不同账号事件、旧revision与迟到全量读取，以及切账号后的迟到回执。既有失败保存、任务保护、分组人数、全局紫色昵称与旧资料保留测试通过。

实际打包APP副本完成性能对照，并通过实际按钮／IPC验证加权、降权、关闭、重启后保存及独立内容busy时仍可操作；测试无凭据复制、无平台采集或模型调用，未替用户修改正式权重。保存的副本原始间隔、星标和批注保持。
