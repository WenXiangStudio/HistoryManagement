# 资料库与区域切换卡顿修复（2026-10-09）

用户反馈点击“博主资料库”及“活跃／普通／低滞＋更新按钮”组件时有零点几秒卡顿，要求修复。已定位、优化并部署到原日常程序，仍为应用0.1.13、连接器0.8.2。

## 原因与修复

当前每组约90～103张卡片。旧实现切换时同时创建整组内容，每张简介在effect中立即读取scrollHeight/clientHeight，并在字体完成、尺寸观察时再次测量，迫使屏幕外卡片也同步排版；CPU采样中这部分是主要阻塞。每次区域切换还创建286～508个Intl.DateTimeFormat实例，每个图标都会新建整份图标JSX。侧栏选中样式的180毫秒transition让较快的页面切换仍显得迟滞。

- 卡片使用`content-visibility:auto`与`contain-intrinsic-block-size:auto 680px`，屏幕外内容跳过排版，保留完整DOM、浏览器查找及可访问性；进入可见区域后正常显示并记忆实际高度。
- 简介观察卡片相对于workspace的位置，只在视口上下200px范围内测量；通过requestAnimationFrame合并同一帧内的测量，保留字体加载及尺寸变化后的重测。离屏停止尺寸观察，卸载取消观察和待执行测量。
- 复用北京时间日期格式化器和静态图标，区域分组按资料、北京时间日期缓存，刷新按钮人数按完整账号名单缓存。不会因缓存漏掉新资料、手动等级改变或跨周统计。
- 移除侧栏选中及分组更新按钮的180毫秒过渡，点击立即反映选中状态。

实现仍只展示当前区域，三个更新范围、搜索、星标、批注、手动权重、勾选刷新等业务规则保留。

## 实测

使用同一份295位日常资料只读副本、同一本地头像和1480×920窗口，对旧归档及最终打包程序各执行5轮连续切换；启用相同CPU采样和计数。以下是点击至目标DOM出现后第二次requestAnimationFrame的中位时间，属于界面绘制机会近似值，不代表屏幕硬件时间或采集全程耗时。

| 操作 | 修复前 | 修复后 |
|---|---:|---:|
| 进入博主资料库 | 27.3 ms | 11.1 ms |
| 活跃区域 | 189.9 ms | 37.0 ms |
| 普通区域 | 191.0 ms | 40.0 ms |
| 低滞区域 | 160.0 ms | 35.3 ms |

区域连续切换耗时减少78～81%。首次打开单独记录：活跃118.4ms（可见头像可用136.1ms）、普通81.6ms（103.3ms）、低滞54.7ms（68.5ms），不能用连续切换中位数描述首次加载。旧版整段对照22个≥50ms长任务，最终版仅首次打开时1个58ms长任务。完整记录与测量边界见公开摘要。
